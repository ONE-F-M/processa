# Processa

## What Processa does

Processa lets a team draw how a piece of work flows (who does what, in which order, and what happens when) and then lets the system run that flow for real.

- **Draw the process.** At `/processa` you draw a process map: steps, decisions, waiting points and hand-offs. The maps use BPMN, the standard notation for business processes.
- **Run the process.** A finished map is deployed. From then on, each time the work starts (for example a new leave request), Processa creates a running copy, called an instance. It hands tasks to the right people, sends emails and chat messages, updates records, and waits for answers.
- **Watch and control it.** At `/processa/instances` you see every running and finished instance, what it is waiting for, and its history. An operator can cancel, suspend, resume or retry an instance.
- **Get AI help.** Several AI assistants live in the editor. ProsAlly draws or changes a map from a plain-language description. Logix writes and fixes the scripts behind automated steps. Other agents run as steps inside maps.

Processa is a Frappe v15 app. The editor is built with [bpmn-js](https://bpmn.io/toolkit/bpmn-js/), and maps run on the [SpiffWorkflow](https://www.spiffworkflow.org/) engine.

The rest of this file is for developers. Coding agents should read [`AGENTS.md`](AGENTS.md) first.

## Installation

### Prerequisites

- Frappe Bench setup
- Node.js 20.x
- Yarn package manager
- For ProsAlly and Logix: an **AI Provider** and an enabled **AI Model** with an API key, linked from the agent's AI Agent Configuration (or a default provider on Processa Settings).

### Install the App

```bash
# Get the app
bench get-app processa <repository-url>

# Install on your site
bench --site your-site.local install-app processa

# Run database migrations
bench --site your-site.local migrate
```

### Build Frontend Assets

```bash
# Navigate to the Vue.js frontend directory
cd apps/processa/frontend

# Install dependencies
yarn install

# Build for production (the editor, then the one-ai bundle)
yarn build

# Copy assets to sites/assets
cd ../../../
bench build --app processa

# Clear cache
bench --site your-site.local clear-cache
```

`yarn build` writes the editor to `processa/public/frontend/` and its page shell to `processa/www/processa.html`.

### Development Mode

```bash
cd apps/processa/frontend
yarn dev --host
```

Access at `http://localhost:8080/processa` (dev server). It forwards backend calls to the bench web server.

## DocTypes

### BPMN Process Model

Stores BPMN process definitions with SpiffWorkflow engine data. Named by the `title` field. **Not submittable.**

| Field | Type | Description |
| ----- | ---- | ----------- |
| `title` | Data (required, unique) | Diagram title (used as the document name) |
| `process_id` | Data (required) | BPMN process ID. The record's value wins: on save, the XML is rewritten to match it. The XML's id is used only when the record has none (the import case). |
| `process_name` | Link to Process | Parent process record |
| `is_active` | Check | Whether the diagram is active (only one active per process) |
| `description` | Small Text | Optional description |
| `bpmn_xml` | Code (XML) | BPMN XML content |
| `decision_tables` | Table | DMN decision tables the map calls |
| `serialized_spec` | JSON | SpiffWorkflow serialized process spec |
| `subprocess_specs` | JSON | SpiffWorkflow subprocess specifications |
| `round_robin_state` | JSON | Round-robin assignment rotation state |
| `version` | Int (required) | Version number |
| `diagram_revision` | Int | Goes up each time the saved XML changes; used to detect stale saves during real-time collaboration |
| `target_doctypes` | Table | DocTypes this process applies to |
| `trigger_type` / `trigger_doctype` / `trigger_event` | Select / Link / Select | Auto-trigger configuration |
| `start_events` | Table | Start-event configuration |
| `deployed_at` / `deployed_by` | Datetime / Link to User | Deployment metadata |
| `process_implementation` | Data | The Process Implementation whose Editable flag decides whether the XML may change |

**Controller logic** (`bpmn_process_model.py`), in `validate()`:

- `validate_is_editable()`: refuses an XML change unless the model's Process Implementation is marked Editable (or a site lock override allows it). Metadata-only changes, Administrator, and trusted callers (import, compile) skip it.
- `sync_process_id_with_xml()`: keeps `process_id` and the XML in step, with the record as the source of truth.
- `enforce_single_active()`: keeps one active diagram per process.
- `validate_script_task_security()`, `validate_response_schemas()` and `warn_unsupported_temperature()`: check Script Tasks and AI Agent Task settings in the XML.
- `bump_diagram_revision()`: raises `diagram_revision` when the saved XML changed.

**Permissions**: System Manager (full), Process Owner (full), All (read-only).

### Data model (other DocTypes)

Beyond the process model, the app defines DocTypes for **execution** (`BPMN Process Instance` for a running execution, `BPMN Active Task` for user-task slots and assignments, `BPMN Activity Log` for the audit trail), plus **supporting configuration** DocTypes for processes, process implementations, process-to-DocType targeting, roles, start events and settings. Canvas comments are stored as standard Frappe `Comment` records. The AI agent DocTypes (AI Agent Configuration, AI Provider, AI Model) and conversation storage (Chat Conversation, Chat Message, Chat Participant, Chat Session State) are part of this app.

## Features

### Home Page (`/processa`)

- Table listing Process records
- Columns: Title, Process Owner, Status, Last Modified, Created
- Status is "Active" when any map of the process is active, "Inactive" when it has maps but none is active, and "No Process Maps" when it has none
- Click a row to open the process editor

### Editor Page (`/processa/process/:process`)

- BPMN modeler powered by **bpmn-js v18**
- **Diagram tab strip** at the bottom: shows the open diagram, a menu listing every map of the process, and a Compare versions button
- Panels for the map's Logix scripts, DMN tables, deployment and configuration (`ProcessLogixTab`, `ProcessDmnTab`, `ProcessDeployTab`, `ProcessConfigurationTab`)
- **Properties panel** (toggleable) with BPMN and SpiffWorkflow properties
- **Formatting toolbar**: font family and size, bold/italic/underline, and text/fill/stroke color pickers
- Toolbar with Undo/Redo/Delete buttons; bpmn-js keyboard shortcuts are on except in read-only mode
- Zoom controls
- Save persists to the Frappe database
- bpmnlint integration with inline problem reporting

The editor has no button to create a new map. Maps are created through `import_bpmn` or `save_process_model`. A map with no XML opens as a blank canvas whose process is `isExecutable="false"`.

Compiled process models run as **process instances** via the SpiffWorkflow engine:

- Start instances manually or via configured triggers, messages and timers
- **User-task assignment** modes: specific User, DocField lookup, Table Field, Round Robin and Load Balancing, with automatic redirect to the reliever of a user on approved leave
- **Service-task automation**: Apply Workflow (Frappe workflow-state transitions), Email Notification, Update Field, Google Chat, Push Notification and Connector (HTTP or Python calls to other systems)
- Frappe ToDo assignments, an activity log, and an instance UI under `/processa/instances`

### SpiffWorkflow Integration

- SpiffWorkflow properties-panel extensions via forked [`bpmn-js-spiffworkflow`](https://github.com/ks093/bpmn-js-spiffworkflow) (`develop` branch)
- **Script editor** for Script Tasks and Pre/Post scripts
- **Markdown editor** for User Task / Manual Task instructions
- **Call Activity editor** for Call Activity elements
- Event-bus handlers for SpiffWorkflow data requests (service tasks, JSON schemas, DMN files, data stores, messages) in `composables/Editor/useEditorSpiffEvents.js`
- Loop data reference fix for multi-instance activities

### Custom Text Styling

- Per-element text formatting (font family, size, weight, style, decoration)
- A custom moddle extension persists styles as XML attributes (`custom:fontFamily`, `custom:fontSize`, and so on)
- A custom renderer applies styles during diagram rendering

### Labels and Translation

- `src/bpmn/aiAgentTranslate.js` shows a Service Task tagged `ai_agent` as an AI Agent Task in the editor.
- Arabic text for user-facing fields is filled in from the English text through `processa.api.translation.translate` (`composables/useArabicTranslation.js`).

### Adding New Features

- **API endpoint**: add to the appropriate submodule in `processa/api/` with `@frappe.whitelist()` (e.g. process CRUD in `process_maps.py`, instance endpoints in `instances.py`).
- **Vue component / view**: add under `frontend/src/components/` or `frontend/src/pages/` and register routes in `frontend/src/router.js`.
- **bpmn-js module**: add under `frontend/src/bpmn/` and register it in `additionalModules` in `frontend/src/composables/Editor/useEditorModeler.js`.
- **Moddle extension**: add under `frontend/src/bpmn/moddle/` and register it in `moddleExtensions` in the same file.

### Runtime Hooks

`processa/hooks.py` registers:

- A universal `doc_events` BPMN trigger on every DocType (`after_insert`, `on_update`, `after_save`, `on_submit`, `on_cancel`, `on_update_after_submit`), so document changes can start or advance processes. A guard runs on `before_submit`, `before_cancel` and `before_workflow_action`, and `on_trash` runs `delete_linked_bpmn_instances` for the document's instances.
- `scheduler_events`. Every minute: BPMN timer start events, timer catch events (`processa/processa_engine/timers.py`) and A2A polling. Other jobs run every 2, 5 or 15 minutes, hourly and nightly; see the `scheduler_events` block for the full list.

## ProsAlly: AI Process Modelling Assistant

ProsAlly is an AI chat assistant in the BPMN editor that helps users create, overwrite and modify process diagrams from plain-language requests.

### Overview

ProsAlly opens as a side panel next to the canvas on desktop (420 px wide by default) and as a bottom sheet on mobile. It runs a multi-step agent pipeline:

```
User prompt
    │
    ▼
Intent Classifier
    │
    ├─ GENERATE_NEW / OVERWRITE_EXISTING / MODIFY_EXISTING
    │       │
    │       ▼
    │   Confirmer  ──► "I'll draw … Shall I proceed?" + [Yes / No, let me adjust]
    │       │  (confirmed)
    │       ▼
    │   Generator / Modifier  ──► intermediate representation ──► compile_ir ──► BPMN XML
    │       │
    │       ▼
    │   Preview card in the chat ──► user clicks apply ──► auto-layout ──► canvas
    │
    ├─ AMBIGUOUS / INCOMPLETE
    │       │
    │       ▼
    │   Clarifier  ──► focused question + option buttons
    │
    └─ IRRELEVANT  ──► polite redirect
```

### Intent Classification

The intents below are defined in the classifier prompt, which patches seed into the database.

| Intent | Trigger | ProsAlly response |
|---|---|---|
| `GENERATE_NEW` | User wants a brand-new process on an empty canvas | Confirms, then generates BPMN |
| `OVERWRITE_EXISTING` | User wants to replace the existing model entirely | Confirms, then regenerates |
| `MODIFY_EXISTING` | User wants to add/remove/change a specific part | Confirms, then changes the existing diagram |
| `AMBIGUOUS` | Multiple valid interpretations | Asks a clarifying question with options |
| `INCOMPLETE` | Clear intent but missing details | Asks for the missing information |
| `IRRELEVANT` | Nothing to do with process modelling | Redirects politely |

### Key Files

| File | Purpose |
|---|---|
| `frontend/src/components/ProsAlly/ProsAllyPanel/ProsAllyPanel.vue` | Wraps the shared chat panel for ProsAlly: sends the canvas XML with each turn and passes an applied diagram to the editor |
| `frontend/src/components/Chat/AgentChatPanel/AgentChatPanel.vue` | The chat UI: messages, option buttons, input |
| `frontend/src/components/Editor/BpmnProsAlly/BpmnProsAlly.vue` | Places the panel beside the canvas (desktop) or in a bottom sheet (mobile) |

| `processa/ai_agent_conversations/chat_persistence.py` | Persists conversation history (`Chat Conversation` DocType) |

### Agent Pipeline

The stages (intent classifier, clarifier, confirmer, generator, modifier) are DB Server Scripts called as Agent Tools by the ProsAlly process map, and their prompts are seeded by patches. The stage scripts import the Python helpers in `processa/ai_agent_registry/definitions/prosally/`. Chat turns go through `processa.api.agui.stream_agent_turn`.

### Auto-Layout (`bpmnLayout.js`)

When the user applies a generated or modified diagram, the editor runs `layoutBpmnXml` on it. For a plain process, the function:

- Parses the XML with `DOMParser` to extract element types, IDs and sequence-flow connections (injecting `<incoming>`/`<outgoing>` references as it goes).
- Runs a BFS + join-relaxation algorithm to assign left-to-right column positions.
- Writes a `BPMNShape` and `BPMNEdge` for every element with the computed positions. The diagram section is built as a string; `XMLSerializer` is used only for the process element.
- Reads the actual `<bpmn:process id="...">` value and uses it as the `BPMNPlane bpmnElement`, so they always match.
- Assigns element dimensions: events 36×36, gateways 50×50, tasks 100×80, sub-processes 200×120.
- Adds `isMarkerVisible="true"` on exclusive-gateway shapes.
- Routes edges with straight connectors (same row), Manhattan L-routing (different rows) and top-arc routing (back-edges / loop-backs).

When the diagram has a pool and lanes, or an expanded sub-process, the function keeps the diagram's own shapes and only adds edges that are missing.

In both cases only the process, the collaboration (if any) and the diagram section are written back. Other root elements, such as messages and signals, are dropped. If the XML does not parse or has no process, it is returned unchanged.

### BPMN Generator Rules

The model writes an intermediate representation (IR), not XML. The pipeline in `frontend/tools/bpmn-pipeline/` turns the IR into BPMN 2.0 that satisfies the active bpmnlint rules:

- `compile.mjs` writes `id="Process_1"` on `<bpmn:process>` and a matching `bpmnElement="Process_1"` on `<bpmndi:BPMNPlane>`, which avoids `no-bpmndi` errors from an ID mismatch.
- Each flow in the IR may carry a condition and a default flag. `compile.mjs` writes the condition as `<bpmn:conditionExpression>` and the default flag as the gateway's `default` attribute. A gateway whose flows have neither still raises a `conditional-flows` warning.
- Placeholder sizes come from `NODE_DIMS` in `shared.mjs`: events 36×36, gateways 50×50, everything else 100×80. The editor's auto-layout then applies its own sizes.

### LLM Configuration

ProsAlly's provider and model come from its **AI Agent Configuration** (`agent_id` `"prosally_agent"`): the linked **AI Provider** and **AI Model**, where the model holds the API key. Without a link, the default provider on **Processa Settings** is used. Supported providers: Anthropic, Google (Gemini) and OpenAI.

### Conversation Persistence

Each chat session is stored as a `Chat Conversation` record. Its `agent_mode` is the agent's `chat_mode_label`, or its `agent_id` when the label is empty. Each turn loads the last `context_max_messages` messages set on the AI Agent Configuration (20 when unset). The `conversation_name` is returned from the backend and kept in the frontend session, so a conversation continues across turns.

### Active Linting Rules

**Errors**

| Rule | Description |
|---|---|
| `start-event-required` | Process must have a start event |
| `end-event-required` | Process must have an end event |
| `no-disconnected` | All elements must have at least one connection |
| `single-blank-start-event` | Exactly one blank (untyped) start event |
| `no-bpmndi` | Every semantic element must have DI (BPMNShape/BPMNEdge) |
| `event-sub-process-typed-start-event` | Event sub-processes need a typed start event |
| `sub-process-blank-start-event` | Sub-processes need a blank start event |
| `ad-hoc-sub-process` | Ad-hoc sub-process structure checks |

**Warnings**

| Rule | Description |
|---|---|
| `conditional-flows` | Gateway outgoing flows must have conditions or a default |
| `no-overlapping-elements` | Shapes must not overlap |
| `label-required` | Elements should have names |
| `no-implicit-split` | Tasks should not have multiple outgoing flows |
| `superfluous-gateway` | Gateways with only one path |
| `no-gateway-join-fork` | Gateways should not both join and fork |
| `event-based-gateway` | Event-based gateway usage checks |
| `no-complex-gateway` / `no-inclusive-gateway` | Discourage complex/inclusive gateways |
| `no-implicit-start` / `no-implicit-end` | No implicit start/end |
| `fake-join` | Detect fake joins |

## Architecture Overview

- `processa/api/`: backend endpoints organized into domain-specific submodules (process CRUD, compilation, instance lifecycle, server scripts, comments, editability, version history, notifications, lookups)
- `processa/processa_engine/doctype/`: BPMN DocTypes and server logic (process models, instances, active tasks, activity logs, configuration); every other module keeps its DocTypes in its own `doctype/` folder
- `processa/processa_engine/agent_runtime/`: the AI agent runtime behind ProsAlly, Logix and the other agents; see its `AGENTS.md`
- `processa/hooks.py`: universal document-event trigger and scheduled jobs (`scheduler_events`)
- `frontend/`: the Vue.js frontend (bpmn-js editor + ProsAlly assistant)
